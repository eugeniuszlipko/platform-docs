# Один репозиторий — другой GitHub-аккаунт (локальная настройка)

> Зачем это вообще нужно: Vercel Hobby-план ограничивает число проектов на
> аккаунт. Когда лимит упёрся, `avocado.kiss` перенесли на отдельный
> GitHub-аккаунт (свой Vercel Hobby-слот) — `cozycorner`/`web.admin`/
> `platform-docs` остались на исходном аккаунте `nowmdr`. Этот документ — как
> локально настроить push/pull под другим аккаунтом для ОДНОГО конкретного
> репозитория, не трогая глобальный git-аккаунт для всех остальных.

## Главный вопрос: повторять на каждый репозиторий?

**Нет — привязка идёт к GitHub-аккаунту, не к репозиторию.** Один SSH-ключ
даёт доступ ко ВСЕМ репозиториям, видимым этому аккаунту. Правило простое:

- **Ещё один репозиторий на ТОТ ЖЕ новый аккаунт** (например, позже решите
  перенести туда и `cozycorner`) → SSH-ключ и алиас в `~/.ssh/config` уже
  готовы, **ничего генерировать заново не нужно** — только повторить шаги
  §3–4 (remote + локальный git identity) для нового репозитория, тем же
  алиасом.
- **Ещё один репозиторий на ДРУГОЙ, третий аккаунт** → GitHub не разрешает
  один и тот же публичный SSH-ключ на двух разных аккаунтах — нужен новый
  ключ и новый алиас (полный цикл §1–4 заново, под своим именем алиаса).

## §1. SSH-ключ под новый аккаунт (один раз на аккаунт)

```bash
ssh-keygen -t ed25519 -C "<email для метки>" -f ~/.ssh/id_ed25519_<метка> -N ""
```
Без passphrase — чтобы push работал не интерактивно. Публичный ключ
(`~/.ssh/id_ed25519_<метка>.pub`) вставляется в новом GitHub-аккаунте:
**Settings → SSH and GPG keys → New SSH key**.

## §2. Host-алиас в `~/.ssh/config` (один раз на аккаунт)

```
Host github-<метка>
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_<метка>
    IdentitiesOnly yes
```

Проверка: `ssh -T git@github-<метка>` → должно ответить
`Hi <username>! You've successfully authenticated...` (exit code 1 — это
нормально, GitHub просто не даёт shell).

## §3. Remote репозитория (на каждый репозиторий под этим аккаунтом)

```bash
cd <репозиторий>
git remote set-url origin git@github-<метка>:<новый-аккаунт>/<репо>.git
git fetch origin
```
Если у нового репо на GitHub уже есть история, которой нет локально (частый
случай при переносе/форке — напр. коммит, сделанный через веб-интерфейс
GitHub при переносе) — **проверить перед пушем**:
```bash
git log -1 --format="%H %s"                 # локальный HEAD
git log -1 origin/main --format="%H %s"      # HEAD на новом remote
```
Если remote просто впереди на несколько коммитов без конфликта — обычный
fast-forward: `git merge --ff-only origin/main`.

## §4. Локальный git identity (опционально, на каждый репозиторий)

Не влияет на доступ/push — только на то, чьё имя стоит в истории коммитов.
**Только локально для этого репо** (без `--global`, чтобы не сломать
identity в остальных репозиториях):
```bash
git config user.name "<имя нового аккаунта>"
git config user.email "<email нового аккаунта>"
```

## §5. Vercel: реконнект Git-интеграции (руками, отдельно от git)

Перенос репозитория на новый GitHub-аккаунт **не** подхватывается
автоматически, даже если аккаунт добавлен в Vercel как коннектор — это два
разных уровня:
1. Аккаунт подключён к Vercel (коннектор) — общая настройка.
2. **Конкретный проект** привязан к **конкретному репозиторию** — это
   отдельная настройка *внутри проекта*, её тоже нужно поправить руками:
   Vercel → проект → **Settings → Git** → отключить старый репозиторий →
   **Connect Git Repository** → выбрать новый.

Также проверить на стороне GitHub: **Settings → Applications → Installed
GitHub Apps → Vercel → Configure** — репозиторий должен быть в списке
Repository access (если приложение стоит в режиме «Only select
repositories»).

После реконнекта Vercel **не деплоит ретроактивно** уже существующие
коммиты — нужен свежий `git push`, чтобы разбудить вебхук (или руками
Redeploy в Vercel → Deployments).

## §6. Ветка `stg` / отдельный домен под неё — нужен Vercel Pro

По умолчанию `<project>.vercel.app` жёстко приклеен к Production. Чтобы
отвязать этот адрес от `main` и отдать его под отдельную ветку (`stg`),
Vercel требует завести **Custom Environment** (Settings → Environments →
привязать к ветке), а затем в Settings → Domains назначить домен на этот
Environment вместо Production. **Custom Environments — фича Pro-плана**, на
Hobby раздела попросту нет. На Hobby ветка `stg` может существовать в git и
получать автоматический preview-адрес вида
`<project>-git-stg-<scope>.vercel.app` — но не тот же `<project>.vercel.app`,
что у прода.
