# Концепт: точечный перезалив внешних картинок в Storage (не реализовано)

> Статус: **идея, зафиксирована 2026-09-17, не реализована**. Ничего в коде/БД
> не менялось. Поднято SEO-аудитом от 2026-09-14 (`cozycorner`, `avocado.kiss`).
> Возвращаться к этому — только по явному решению, отдельным точечным заходом.

## Ситуация

Оба сайта осознанно рендерят внешние картинки (Amazon-фото товаров, Unsplash)
с `unoptimized: true` в `next.config.ts` — см. cozycorner.md §4 / avocado-kiss.md
§4. Это **не баг, а действующая политика**: широкий `remotePatterns` тратил бы
метрируемую квоту Vercel Image Optimization на непредсказуемые чужие CDN и делал
бы `/_next/image` открытым прокси. **Эту политику менять не предлагается.**

Цена политики: `unoptimized` = браузер получает оригинальный файл как есть, без
ресайза/переформатирования — независимо от того, каким мелким он показан на
странице. SEO-аудит нашёл конкретный пример на проде (не тестовые данные):
hero-фото рецепта Avocado Kiss с `images.unsplash.com` весит **≈2.8 MB** — для
сравнения, аналогичное фото через собственный `avocado-kiss-photos` (Supabase
Storage → `next/image`) весит **≈150 KB**. Для страниц, которые как раз должны
хорошо ранжироваться и не тормозить LCP, это заметный минус.

## Концепт решения

Не трогать `unoptimized`/`remotePatterns` глобально, а **точечно перезаливать**
отдельные картинки (в первую очередь — hero-фото у реального, опубликованного
контента, который важен для SEO/перфоманса) в собственный бакет сайта
(`cozycorner-photos` / `avocado-kiss-photos`), с заменой внешнего URL в
`image_path`/`hero_image_path` на плоский ключ бакета. Как только картинка живёт
в своём Storage — она автоматически идёт через уже разрешённый `next/image`
(хост `*.supabase.co` в `remotePatterns` уже есть), без единой правки конфига.

## Как технически это можно сделать (проверено, не выполнено)

1. Скачать оригинал по внешнему URL.
2. Залить в нужный бакет через Supabase Storage REST API, авторизуясь
   `SUPABASE_SERVICE_ROLE_KEY` (cozycorner) / `SUPABASE_SECRET_KEY` (avocado.kiss)
   — оба лежат локально в `.env.local` соответствующего репо, server-only.
   Обычный anon/publishable-ключ для записи не годится: RLS на
   `storage.objects` разрешает `INSERT` только `authenticated` + `is_admin()`
   (проверено `pg_policies` 2026-09-17) — сервисный ключ обходит это осознанно
   и точечно, не как постоянный канал записи.
3. Обновить `image_path`/`hero_image_path` у соответствующей записи (через
   `cozycorner-content-ops`/`avocado-content-ops` скилл, не сырым SQL мимо
   гайдрейлов).
4. Убедиться, что `media`-таблица (source of truth медиа-менеджера) не
   рассинхронизирована — файл залит по-настоящему, не просто выдуманная запись.

⚠️ Сервисный ключ обходит все RLS — использовать его для этого сценария
осознанно и узко (конкретные файлы по запросу), не как автоматический обход
всего каталога без ревью.

## Известные кандидаты (по аудиту 2026-09-14, ещё актуальны на 2026-09-17)

- **Avocado Kiss** — рецепт «Sourdough toast with smashed avocado and eggs»
  (hero с Unsplash, ≈2.8 MB) и товар `cast-iron-grill-pan` (тоже Unsplash) —
  два конкретных, проверенных примера.
- **CozyCorner** — риск шире и не проинвентаризирован: неизвестно, сколько
  товаров ссылаются на Amazon-фото напрямую вместо `cozycorner-photos`. Нужен
  отдельный проход (`select` по `products.image_path not like '%supabase%'`
  или аналогично), прежде чем решать масштаб перезалива.

## Не делать без явного решения

- Не заливать «весь каталог» скопом — точечно, по конкретным находкам.
- Не менять `unoptimized`/`remotePatterns` в `next.config.ts`.
- Не использовать сервисный ключ ни для чего, кроме этой конкретной задачи,
  без отдельного запроса.
