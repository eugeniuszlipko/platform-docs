# Мета: когда включать Superpowers

> Superpowers — это **процесс агента** (как проектировать, планировать, исполнять и проверять). `meta-planning` — **формат общения с владельцем**. Они не заменяют друг друга: Superpowers наполняет агентскую спеку и работу, `meta-planning` определяет, как всё это показывается владельцу.
> Superpowers — тяжёлая машина: окупается на крупных многофайловых фазах, на мелочах только тратит токены. По умолчанию он **выключен**; тяжёлые скиллы грузятся только на уровне 3.

## 1. Уровни и сигналы

| Уровень | Сигналы (достаточно одного из более высокого уровня) | Что делаем |
|---|---|---|
| **1. Лёгкий** | Цвет, шрифт, отступы, сдвиг элементов, текст, код аналитики, мелкий ресёрч, правка одного файла, эксперимент «попробовать и посмотреть». **Не** затрагивает БД, права, деплой-конфиги | Работаем сразу, без Superpowers и без спеки. В конце `build` + `lint` (если менялся код). Отчёт короткий |
| **2. Средний** | Баг или фича в одном репозитории без миграций; падающий тест; «странное поведение»; нужно объяснить причину | `systematic-debugging` (баги) + `verification-before-completion` (перед «готово»). Без плана и спеки. Ревьюеры ECC — по таблице корневого `AGENTS.md`, если заметно менялись `.tsx`/`.ts` |
| **3. Крупный** | Любое из: миграция / RLS / новая таблица; два и больше репозитория (сайт + `web.admin` + доки); админка вместе с сайтом; новый тип страницы/раздела; внешний сервис или интеграция; требования с открытыми решениями по данным, маршрутам или внешнему виду; ориентировочно >5 файлов; команда «Начинаем фазу N» | Полный путь §3 |

Пороги ориентировочные (владелец: «потом поправим»). При сомнении между двумя уровнями выбирай **более лёгкий**, но миграции, RLS, права и деплой — всегда уровень 3.

## 2. Кто решает уровень

1. **Команда владельца главнее всего:**
   «по-быстрому» / «без Superpowers» → уровень 1; «средне» → 2; «по-полному» / «используй Superpowers» → 3.
   Если «по-быстрому» затрагивает миграцию/RLS/права — выполни, но одной строкой предупреди о риске.
2. **«Начинаем фазу N»** → уровень 3 без вопросов.
3. **Иначе оцени сам** по таблице. Явный уровень 1 — просто делай, про Superpowers не упоминай.
4. **Если оценка выше, чем владелец описал** (или задача выросла по ходу) — остановись и предложи опросником (`AskUserQuestion`, формат `meta-planning` §3: заголовок «Уровень», вариант-рекомендация первым, у каждого варианта строка последствия):
   «По-полному (Recommended)» — спека + план + ревью, дороже по токенам, меньше риска; «Средне»; «По-быстрому» — быстро, без плана, риск лишней переделки.
   Один вопрос, без пересказа таблицы.
5. Решение действует до конца задачи. Если задача выросла — повтори п. 4.

## 3. Уровень 3 — путь

> Этапы идут в **отдельных чатах** («Планируем фазу N» → «Начинаем фазу N» → «Принимаем фазу N», `meta-planning` §5): шаги 0–2 ниже относятся к планированию, 3–8 к исполнению. Цель — держать контекст в районе 200k; замеры 2026-10 — в `platform-docs/methodology/superpowers-evaluation-2026-10.md`.

0. **Контекст.** `AGENTS.md` репозиториев, память, документы фазы в `platform-docs`. Скиллы ECC — по таблице корневого `AGENTS.md`. Если фаза зависит от внешних знаний (актуальные подходы, выбор библиотеки или сервиса, свежие изменения фреймворка) — один раз субагент `researcher` (плагин `agent-kit`) с конкретным вопросом; поиск внутри кода — `Explore`.
1. **Дизайн.** Загрузи `brainstorming` (территория вопросов, builder-check субагентом). Вопросы владельцу **только** по `meta-planning` §3. Результат — агентская спека `platform-docs/sites/<проект>/specs/<дата>-phase-N-<имя>-spec.md` и по ней план владельца из 7 разделов в `plans/` (`meta-planning` §2). Статус «ждёт ваших ответов» → «ждёт утверждения».
2. **Стоп.** «Утверждаю» не запускает код. Старт — только «Начинаем фазу N».
3. **Impl-план — только если есть миграция/RLS/новая таблица ИЛИ работа идёт в двух и более репозиториях** (решение владельца 2026-10-18; замеры: impl-план стоит 1–2% расхода, но для фазы без БД и с одним репо хватает спеки с перечнем шагов). Тогда `writing-plans`: `specs/<дата>-phase-N-<имя>-impl-plan.md`, **по одному плану на репозиторий**. Иначе `writing-plans` не загружай: исполняй по шагам агентской спеки. Способ исполнения не спрашивай: выбери по рекомендации (`subagent-driven-development` — много задач с общими интерфейсами или цена ошибки высока; `executing-plans` — иначе) и впиши выбор в «Что решил сам»/ответ на старт. `brainstorming` пропускай, если спека уже утверждена.
4. **Ветка** (см. §5): в каждом затронутом репозитории `feat/<slug>` от `main`.
5. **Исполнение.** `subagent-driven-development` или `executing-plans`, скрипты запускай **из корня целевого репозитория**. Технические развилки решай сам и записывай; развилка, меняющая **данные, маршруты, внешний вид/тексты, бизнес-правила или стоимость**, — стоп и вопрос владельцу (`meta-planning` §4).
6. **Ревью-гейт — один ревьюер на слой** (решение владельца 2026-10-18; в фазах 3–6 ревьюеры сильно пересекались, одни и те же находки приходили от двух-трёх). Сначала ревью на соответствие плану (`requesting-code-review`, его запускают скиллы исполнения), затем **один раз** ревьюеры по таблице «Ревьюеры по слоям» в `platform-docs/skills/ecc/README.md`, включая `security-auditor` при изменениях доступа к данным, API-роутов, токенов/env, форм, вывода HTML/JSON-LD из БД (не при стилях). Его Critical/High исправляет исполнитель, затем повторный прогон проверок. Один запуск каждого типа на репозиторий за фазу; повторный — только после исправления CRITICAL/HIGH и только по изменённым файлам. CRITICAL/HIGH — исправить или вынести владельцу. Ревьюеры не заменяют `build` + `lint` + `test`.
7. **Проверка.** `verification-before-completion`: `build`, `lint`, `test` в каждом затронутом репозитории с реальным выводом — прогон делает субагент `qa-runner` (возвращает сжатые доказательства, логи не оседают в основном контексте); e2e — если фича это пользовательский флоу. **Для каждого среза, меняющего то, что видит посетитель, — проверка на телефоне 390 px** (`platform-docs/methodology/testing.md` → «Проверка на телефоне»); в отчёте указать, что проверено на 390 px, или что не проверялось. e2e не должны зависеть от живых данных (там же → «e2e и живые данные»).
8. **Документация и отчёт.** Обновление `platform-docs` (схема, доки админки, бэклог) — субагент `docs-writer` по фактам из diff и решений фазы. Отчёт по `meta-planning` §8. Раздел «Что изменилось по сравнению с планом» обязательно включает все принятые решения-«ruling» и отложенные minor-замечания. Дальше ждём «принято».

## 4. Тесты (решение владельца 2026-10-16)

TDD из Superpowers целиком **не включаем** (исследования не показывают выигрыша по качеству для агентов, а токенов уходит в разы больше; у нас независимые тесты по спеке от `test-engineer`). Берём два случая:
- **Баг** → сначала один падающий тест, воспроизводящий баг, потом фикс.
- **Чистая логика** (резолверы, санитайзеры, форматтеры) → тест можно писать первым.

Всё остальное: реализация, затем тесты по спеке (скилл `testing`, субагент `test-engineer`; код не меняет, расхождения со спекой возвращает отчётом). Правило «удали код, написанный до теста» **не действует**.

## 5. Git (решение владельца 2026-10-16)

- Ветка на фазу в каждом затронутом репозитории: `feat/<slug>` (или `feature/<slug>`, как уже принято в репо). **Не работать в `main`.**
- **Worktrees не используем:** в новом worktree нет `node_modules` и `.env.local`, а e2e нужен живой Supabase.
- На feature-ветке допустимы **локальные коммиты** по задачам. **`push`, merge, PR, удаление веток — только по явной команде владельца** (деплой привязан к пушу). Коммиты (код и документы `platform-docs`) делает субагент `committer` в конце среза/задачи/фазы (решение владельца 2026-10-29: история читаемая и удобная для агентов). Перед просьбой о push — одной строкой на репо: проект → ветка → уйдёт ли на прод (колонка «Push в `main`» реестра).
- Скилл `finishing-a-development-branch` не взят (он про worktree) — см. «Завершение».

## 6. Завершение (вместо finishing-a-development-branch)

После «принято» предложи три варианта (опросником): 1) merge в `main` локально, 2) push + Pull Request, 3) оставить ветку как есть (по умолчанию). Перед merge/PR — прогнать тесты на итоговом дереве и подтвердить базовую ветку. Выполняй только выбранное. Удаление/отбрасывание работы — только по прямой просьбе и после слова `discard`.

## 7. Что из Superpowers НЕ используется

Плагин-режим и хук `SessionStart` (`using-superpowers`: принудительно тянет процесс на каждую задачу), `using-git-worktrees`, `test-driven-development`, `finishing-a-development-branch`, визуальный компаньон brainstorming, `dispatching-parallel-agents`, `receiving-code-review`, `writing-skills`, `diagnosing-superpowers`. Плагин `superpowers@claude-plugins-official` (v5.0.7) остаётся **выключенным**: включать его не нужно, иначе хук продублирует и усилит всё это на мелочах.

## 8. Чего не делать

- Запускать Superpowers на уровне 1 или объяснять владельцу, «каким скиллом» ты работаешь.
- Отправлять владельца читать спеку, план или impl-план (`meta-planning` §3a): ему задают ключевые вопросы, остальное решает агент.
- Запускать несколько ревьюеров одного слоя «для надёжности» (см. п. 6).
- Менять формат вопросов и плана ради Superpowers: он подстраивается под `meta-planning`, не наоборот.
- Пропускать «утверждаю» и «Начинаем фазу N» из-за правила Superpowers «continuous execution».
- Принимать решения за владельца по данным, маршрутам, внешнему виду, бизнес-правилам, стоимости под видом «ruling».
- Коммитить в `main` деплоящихся репо, пушить и мержить без явной команды.
- Править вендоренные файлы вне блока Workspace notes (обновление — только ре-вендорингом, см. `platform-docs/skills/superpowers/README.md`).
