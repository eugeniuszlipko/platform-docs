# B-016 — Поиск Urban: RPC `search_content` читает всю таблицу, стоимость растёт линейно с каталогом

**Что (замер фазы Z, 2026-10-20).** Функция поиска в базе не использует GIN-индексы `pg_trgm` (условия внутри `greatest(case …)`, без индексируемого предфильтра — это было известно с миграции 0024). Замер на временных копиях таблиц (`pg_temp`, без записи в реальные таблицы), среднее по 5 вызовам:

| Каталог | 1 слово | 2 слова | 6 слов |
|---|---|---|---|
| сейчас (12 статей / 10 товаров) | 3 мс | 4 мс | 5 мс |
| 480 / 400 | 41–46 мс | 89 мс | 122 мс |
| 1080 / 900 | 92–102 мс | 200 мс | 279 мс |

Функция открыта для `anon`, лимита частоты на стороне базы нет. На сегодняшнем объёме проблемы нет (3 мс); при ~1000 статей и ~1000 товаров один запрос ≈ 0,1–0,3 с процессорного времени, и всплеск запросов (бот, нажатия клавиш) начнёт упираться в CPU базы.

**Уже сделано в фазе Z (клиент):** в базу уходит не больше одного запроса панели за раз (раньше — по запросу на символ, до 7 параллельных), промежуточный текст пропускается, повторный запрос берётся из памяти вкладки на 60 с.

**Предложение (когда понадобится).** Колонка `search_doc` (сводный нижний регистр: название + подзаголовок + анонс + темы + бренд/категории) с одним `gin_trgm_ops`, предфильтр `search_doc ilike pat` перед подсчётом баллов; для карточек — отдавать их тем же RPC (убирает второй круг запросов, ≈ 0,3 с на холодной сети). Это миграция → уровень 3, `database-reviewer`.

**Порог для возврата:** > ~300 статей или > ~300 товаров, либо жалобы на задержку поиска.

**Нужно решение владельца:** нет (технический долг с порогом). **Статус:** новая.
