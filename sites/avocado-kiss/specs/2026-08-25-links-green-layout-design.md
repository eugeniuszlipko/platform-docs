## 1. Задача A — ссылки соцсетей

### 1.1 Диагноз

На скриншоте пользователя иконка Instagram в шапке и пункт «Instagram» в футере
окрашены иначе остальных, а в футере ещё и подчёркнуты. Оба симптома — признаки
состояния **`:visited`**: Instagram у пользователя посещён, X и Pinterest — нет.
Проверка живого сайта (`avocado-kiss.vercel.app`, Playwright, computed styles)
подтверждает исходные условия:

| Поверхность | Селектор | Текущий вычисленный `color` | Проблема |
|---|---|---|---|
| Шапка | `Header.module.css:37` `.socialLink` | `color(srgb 0.043 0.11 0.173 / 0.75)` | **полупрозрачный** + современный цветовой синтаксис |
| Бургер | `MobileMenu.module.css:135` `.socialLink` | то же | то же |
| Футер | `Footer.module.css` `.link` | `rgb(11, 28, 44)` — из `a { color: inherit }` | **нет собственного `color`**, живёт на `inherit` |

Механизм: при вычислении стиля `:visited` браузер работает в «ограниченном»
режиме приватности — применяется урезанный набор свойств, значения приводятся к
непрозрачным, а то, что резолвер не может выдать в этом режиме (альфа,
`color-mix()`, `color(srgb …)`, цепочка `inherit`), отбрасывается, и в дело идёт
дефолтный «посещённый» цвет UA. Подчёркивание в футере дополнительно указывает,
что на том браузере авторские правила ссылок частично не выиграли — типично для
режима «переопределять цвета страницы» / forced-colors.

**Правил `:link` / `:visited` в проекте нет ни одного** — единственная защита это
`a { color: inherit; text-decoration: none }` в `globals.css:145-148`, которой при
ограничениях `:visited` недостаточно.

Тот же дефект класса затрагивает и обычные ссылки навигации, построенные на
`color-mix()`: `Header.module.css:105` `.navLink` (80%) и `MobileMenu.module.css:88`
`.link` (88%) — после посещения категории они уедут в тот же дефолтный цвет.
Чиним заодно: правка идентична и однострочна.

### 1.2 Решение

**Принцип: у каждой ссылки цвет задан явно, непрозрачным литералом, и одинаков во
всех состояниях кроме `:hover`/`:focus-visible`. Индикация посещённости не нужна.**

Новые токены в `:root` (`globals.css`) — плоские значения тех же `color-mix()`,
посчитанные поверх `--background: #fcfaf6`, так что на экране ничего не меняется:

```
--icon-muted: #47545f;  /* = foreground 75% над background — иконки соцсетей */
--nav-link:   #3b4854;  /* = foreground 80% — пункты навигации в шапке        */
--menu-link:  #283745;  /* = foreground 88% — пункты бургер-меню              */
```

Глобальный предохранитель в `globals.css` — **отдельным правилом и обязательно
через `:where()`**, правило `a` остаётся как было:

```css
a {
  color: inherit;
  text-decoration: none;
}

/* Предохранитель: те же значения для посещённых ссылок. :visited вычисляется
   браузером в ограниченном режиме приватности, и всё, что резолвер там выдать не
   может (альфа, color-mix(), color(srgb …)), отбрасывается с откатом к дефолтному
   цвету UA — поэтому состояния названы явно. */
a:where(:link, :visited) {
  color: inherit;
  text-decoration: none;
}
```

> **Почему `:where()` — не косметика.** Первая реализация написала это как
> `a, a:link, a:visited { … }` и внесла регрессию: голый `a:link` имеет
> специфичность **(0,1,1)** против прежних (0,0,1) у `a`, то есть перебивает
> **любой одноклассовый цвет ссылки в CSS-модулях** — все они (0,1,0). На
> `/blog` это перекрасило чипы фильтра в `inherit`: неактивные потеряли
> `--muted-foreground` и стали чёрными, активный потерял светлый текст и стал
> чёрным на зелёной заливке (белым он оставался только на ховере, где
> `.active:hover` (0,2,0) снова выигрывал). `:where()` обнуляет вклад
> псевдоклассов — правило остаётся (0,0,1), ровно как `a`, и перебить компонент
> не может. Отдельным правилом, а не одним списком: браузер без поддержки
> `:where()` отбросит только предохранитель, а базовое `a` уцелеет.
>
> Общий вывод для этого проекта: **глобальные правила для `a` должны оставаться
> нулевой/минимальной специфичности**; устойчивость к `:visited` даётся точечно,
> на уровне компонента, где специфичность и так выше.

Точечно, на каждой из трёх поверхностей — вместо одного правила `.socialLink`
пара правил (базовое состояние + ховер), покрывающая `:link` и `:visited`:

```css
.socialLink,
.socialLink:link,
.socialLink:visited {
  color: var(--icon-muted);
  text-decoration: none;
}

.socialLink:hover,
.socialLink:focus-visible {
  color: var(--accent);
}
```

Аналогично: `Footer .link` (получает явный `color: var(--foreground)` вместо
`inherit`), `Header .navLink` → `--nav-link`, `MobileMenu .link` → `--menu-link`,
`MobileMenu .socialLink` → `--icon-muted`.

Внутри иконок ничего не трогаем: SVG рисуются `stroke="currentColor"` и наследуют
`color` ссылки — как только `color` стал устойчивым, устойчив и штрих.

### 1.3 Что НЕ делаем

- `forced-colors: active` блок не добавляем (пользователь выбрал вариант без него):
  в режиме высокой контрастности ссылки останутся системными — это осознанный
  a11y-дефолт, а не баг.
- `ShareButtons` не трогаем в части `:visited`: `.button` — это `<button>`, а
  `.menuItem` уже имеет непрозрачный `color: var(--foreground)`. Глобальное правило
  их накрывает бесплатно.
- URL соцсетей и `site_settings` не трогаем.

### 1.4 Порядок иконок

`buildSocials()` в `lib/socials.ts` строит массив `defs` в фиксированном порядке —
это единственный источник порядка для шапки, футера и бургер-меню сразу.

```
было:  X → Pinterest → Instagram
стало: Instagram → X → Pinterest
```

Правится порядок элементов массива `defs` + шапка-комментарий файла (строки 8-9
явно фиксируют старый порядок). `SocialKey`, `SOCIAL_ICONS`, типы и логика
«сеть без URL не рендерится» — без изменений.

**Тест:** `lib/socials.test.ts` содержит `it("returns X, Pinterest, Instagram in
that fixed order")` с двумя `toEqual` на порядок и `it("drops networks whose url
is null")` (ожидает `["X (Twitter)", "Instagram"]` при выключенном Pinterest →
станет `["Instagram", "X (Twitter)"]`). Оба обновляются под новый порядок — это
изменение спеки, а не поломка.

## 2. Задача B — зелёный

### 2.1 Аудит (сделан, результат зафиксирован)

Прогон всех вычисленных цветов живого сайта на `/blog` и на странице рецепта со
steps (Playwright, `getComputedStyle` по `color`/`background`/`border`/`fill`/
`stroke`/`outline` каждого узла) даёт **ровно один зелёный: `rgb(70, 119, 72)` =
`#467748` = `--accent`**. Чип фильтра блога (`BlogFilters .active`, зелёный фоном)
и номер шага рецепта (`RecipeContent .stepNumber`, зелёный текстом) — это один и
тот же цвет; разница воспринимается из-за разной формы подачи (заливка pill'а
против тонкого текста 24px), а не из-за оттенка.

Второй зелёный `#3f6b46` в репозитории существует, но **только** как CSS-фолбэк в
макете `mockups/version-2/avocado-kiss-home.html:18` — в сборку не попадает.

Вывод: перекрашивать нечего. Реальная непоследовательность в другом — производные
оттенки зелёного разбросаны инлайновыми `color-mix()` без имён.

### 2.2 Решение

Два новых токена в `:root`, значения 1:1 равны текущим `color-mix()`:

```
--accent-border: #90a78c;                /* = accent 50% + --border; рамка чипа/карточки на ховере */
--accent-soft:   rgba(70, 119, 72, 0.08); /* = accent 8%; подложка ховера кнопок и пунктов меню   */
```

`--accent-soft` остаётся полупрозрачным намеренно: он ложится на разные
поверхности (`--background` в ShareButtons-ряду, `--card` во всплывающем меню) и
должен подстраиваться. `:visited`-ограничения его не касаются — это `background`
у `<button>`/`role="menuitem"`, не цвет ссылки.

Замены (4 файла, 5 строк):

| Файл:строка | Было | Стало |
|---|---|---|
| `BlogFilters.module.css:24` | `color-mix(in srgb, var(--accent) 50%, var(--border))` | `var(--accent-border)` |
| `RecipeCardLink.module.css:19` | то же | `var(--accent-border)` |
| `ShareButtons.module.css:43` | `color-mix(in srgb, var(--accent) 8%, transparent)` | `var(--accent-soft)` |
| `ShareButtons.module.css:121` | то же | `var(--accent-soft)` |

Комментарий у `--accent-border` фиксирует происхождение значения (смесь с
`--border`), потому что токен плоский и при смене `--border` не пересчитается сам.

Все прочие `var(--accent)` (49 вхождений) остаются как есть — они уже
стандартизованы.

### 2.3 Чипы фильтра блога — состояния

`BlogFilters` — единственное место в проекте, где цвет ссылки задан классом и при
этом есть два взаимоисключающих состояния (`.chip` / `.chip.active`). Правится
вместе с §1.2:

- `.chip` и `.active` **оба** получают тройку `:link`/`:visited`. Покрыть только
  `.chip` нельзя: он станет (0,1,1) и перебьёт `.active` (0,1,0) — активный чип
  снова потеряет светлый текст.
- `.chip:hover` дополняется `:focus-visible` (клавиатурный паритет, как у
  соцссылок).
- `.active:hover, .active:focus-visible` **повторяет `background` и
  `border-color`**, а не только `color`. Иначе `.chip:hover` (0,2,0) кладёт
  поверх зелёной заливки бледный `--accent-border`, и вокруг пилюли появляется
  светлое кольцо. Активный чип на ховере не меняется вовсе — это текущий фильтр,
  нажимать его незачем.

Проверено в браузере: неактивный чип `#576574` → ховер зелёный текст +
`--accent-border` рамка; активный `--accent-foreground` на `--accent` и в покое,
и на ховере.

## 3. Задача C — sticky-футер

### 3.1 Проблема

`https://avocado-kiss.vercel.app/category/pasta` с тремя карточками: контента
меньше высоты экрана, `body` — обычный поток, поэтому футер встаёт сразу под
сеткой и под ним остаётся пустая полоса фона. `min-height: 100vh` стоит на самом
`body`, но не распределяется между шапкой, контентом и футером.

### 3.2 Решение

Правится **только** `globals.css`, глобально для всех страниц — задача одинакова
везде, где контента мало (`/category/*`, `/search` без результатов, `404`).

```css
body {
  min-height: 100svh;      /* было 100vh */
  display: flex;
  flex-direction: column;
}

/* Контент занимает всё, что осталось между липкой шапкой и футером: на коротких
   страницах (пустая категория, поиск без результатов) футер прижат к низу окна,
   а не висит под последней карточкой. */
body > main {
  flex: 1 0 auto;
}
```

Селектор `body > main` работает без обёртки: **каждая** страница проекта рендерит
`<main>` первым элементом (проверено — 11 из 11: `page.tsx`, `not-found.tsx`,
`blog`, `shop`, `shop/[category]`, `category/[slug]`, `product/[slug]`,
`recipes/[slug]`, `search`, `about`, `contact`). Если когда-нибудь появится
страница без `<main>` — деградация ровно в текущее поведение, без поломки.

`100svh` вместо `100vh` — по той же причине, по которой `100svh` уже используется
в проекте для полноэкранных секций (см. комментарий у `--header-h`): на мобильных
`100vh` считается по развёрнутому окну и даёт лишнюю прокрутку.

### 3.3 Риски и что проверить

`display: flex` на `body` — единственное место, где эта правка может задеть
что-то ещё. Проверить глазами и e2e:

- **липкая шапка** (`position: sticky; top: 0` внутри flex-контейнера) — не
  должна отклеиться ни на одной странице;
- **`overflow-x: clip`** на `html, body` (комментарий в `globals.css` предупреждает,
  что `hidden` ломает sticky) — остаётся как есть;
- **полноширинные секции** — `HeroCarousel` (`--hero-slider-max`, шире контентного
  контейнера), `NewsletterBlock` (инверсный фон во всю ширину), `MosaicBanner`:
  flex-элементы по умолчанию `align-self: stretch`, ширина не должна измениться;
- **бургер-меню**: оверлей ставит `documentElement.style.overflowY = 'hidden'` —
  поведение не зависит от раскладки `body`, но проверить открытие/закрытие;
- **длинные страницы** (`/`, рецепт, статья) — визуально без изменений.

## 4. Задача D — админка: лейблы формы Article

Чисто фронтовое переименование в `web.admin`, **имена полей БД и Zod-схемы не
трогаем** (`hero_image_path`, `hero_caption` остаются): контракт
`admin-panel/blog-avocado-kiss.md`, слой данных и сайт продолжают работать как
есть.

| Файл:строка | Было | Стало |
|---|---|---|
| `ArticleEditPage.tsx:248` | `<FieldLabel htmlFor="hero_image_path">Hero image</FieldLabel>` | `Cover image` |
| `ArticleEditPage.tsx:269` | `<FieldLabel htmlFor="hero_caption">Hero caption</FieldLabel>` | `Image caption` |
| `ArticleEditPage.tsx:211` | `alt={form.watch('title') \|\| 'Hero image'}` | `'Cover image'` (фолбэк alt превью) |

`htmlFor`/`id`/`register('…')` остаются прежними — связь label↔input не рвётся.

Прецедент уже есть: в `AvocadoPageEditPage.tsx:211` то же поле `hero_image_path`
называется «Background image» — там оно и правда фон hero-баннера страницы, а в
статье это обложка материала, отсюда разные имена. Поля
`Hero eyebrow`/`Hero title`/`Hero description` в `CategoryEditDialog.tsx` и
`Hero banner`/`Hero sections` в `AvocadoPageEditPage.tsx`/`HeroSectionsEditor.tsx`
**не переименовываем** — там «hero» описывает секцию страницы, а не картинку, и
задача про них не ставилась.

**Тесты:** `ArticleEditPage.test.tsx` обращается к полю по видимому лейблу —
`queryByLabelText('Hero caption')` в трёх кейсах (строки 58, 64, 70) и название
кейса на строке 53 (`'essay: no Subtitle, no Hero caption'`). Обновляются на
`Image caption`.
