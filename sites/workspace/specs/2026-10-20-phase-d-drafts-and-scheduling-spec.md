## D2 — scheduled publishing
1. **DB:** `publish_at timestamptz null` on the 7 tables: `cozycorner.posts`, `cozycorner.products`, `avocado_kiss.posts`, `avocado_kiss.recipes`, `avocado_kiss.products`, `urban_gardener.articles`, `urban_gardener.products`. Check: `publish_at is null or not is_published` (scheduled implies draft). Partial index `where publish_at is not null and not is_published`. Not readable-by-anon relevance: column is harmless but include in anon column grants consistently with the token pattern.
2. **Flipper:** one `public.publish_due_content()` — `security definer`, `set search_path = ''`, revoke execute from public/anon/authenticated (grant only to postgres/service_role); for each of the 7 tables: `update … set is_published = true, published_at = publish_at, publish_at = null where publish_at <= now() and not is_published`. Per-table (and ideally per-row) `exception when others` so one violating row (e.g. Urban `products_published_needs_photo_link`) does not block the rest; on failure leave `publish_at` set and log (small `publish_log` table or `raise warning`; owner wants no notifications — log only, visible to the agent via `query_logs`). Install extension `pg_cron`, `cron.schedule('publish-due-content','* * * * *', …)`. Idempotent migration (`cron.unschedule` if exists). Note: `pg_cron` lives in schema `pg_catalog`/`cron`; job runs as the creating role — confirm grants; confirm Supabase dashboard Integrations → Cron is OK with SQL-created job.
3. **Admin:** third status «Scheduled» with datetime-local (browser tz; show tz label, e.g. `GMT+2`); store ISO/UTC; validation: must be in the future (past ⇒ treated as Published with that `published_at`, as today), must satisfy publish preconditions (Urban product photo+link) at save time. Status derivation: `is_published` → Published; `!is_published && publish_at` → Scheduled; else Draft. Draft ⇒ clear `publish_at` (cancels). Urban `save_article`/`save_product` RPCs get `publish_at` (migration), Cozy/Avocado go through direct table writes — keep one TS helper `derivePublishState(values)` and test it (pure logic, test-first allowed). List badges «Scheduled · <local date/time>».
4. **Skills:** content-ops skills get a `publish_at` section (ISO with offset; must be future; state stays `is_published=false`).
5. **Verify:** real run — schedule a throwaway record +3 min on each site's table via admin/SQL on a non-prod row? Prefer: apply on base-one (the only DB), use a clearly named test row, watch it flip, delete it. ISR delay ≤2 min measured and reported. `get_advisors` (security + performance) after migration.
